## 3. Real accounts: passwords, logins and ownership

Replaces the old setup, where an account was a uuid the browser remembered and sent in an `X-User-Id` header that the server trusted.

### Server

| File | Change |
|---|---|
| `migrations/1791800000000_passwords-and-sessions.js` (new) | Adds `users.password_hash` (nullable) and a `sessions` table (token hash, user, created, expires). RLS on. Deleting an account deletes its sessions. |
| `src/auth.ts` (new) | Password hashing with scrypt (N=2^17, r=8, p=1) and a random 16-byte salt, via Node's built-in `crypto`. Constant-time comparison. 32-byte random session tokens, stored only as SHA-256. |
| `src/models/sessions.ts` (new) | Create a session (7 days), look up the account for a token, delete a session. |
| `src/require-user.ts` (new) | Middleware: reads `Authorization: Bearer <token>`, answers `401` without a valid one. |
| `src/models/users.ts` | `create` takes a password and stores only its hash. New `findForLogin`. `list` removed. |
| `src/controllers/users.ts` | New routes, listed below. |
| `src/controllers/regimes.ts`, `onboarding.ts` | Every route requires login. `X-User-Id` removed. |
| `src/models/regimes.ts` | `get`, `update` and `remove` now only find a plan for its owner (`and user_id = $2`). Removes the "NO OWNERSHIP CHECK EXISTS" TODOs. |
| `src/app.ts` | Mounts `/api/sessions`. CORS allows `Authorization` instead of `X-User-Id`. |

**Routes now:**

| Route | What it does |
|---|---|
| `POST /api/users` | Sign up with `{username, password}`; returns `{user, token}` |
| `POST /api/sessions` | Log in; `401` "wrong username or password" either way |
| `DELETE /api/sessions` | Log out; the token stops working |
| `GET /api/users/me` | The logged-in account |
| `DELETE /api/users/me` | Delete the account, with its plans, questionnaires and sessions |

**Removed:** `GET /api/users` (listed every account), and `GET` / `DELETE /api/users/:id`.

**Security details:**
- Another account's plan or questionnaire is a `404`, the same as one that doesn't exist.
- A wrong password and an unknown username get the same message and take about the same time, so the form can't reveal who has an account.
- Passwords are 8–128 characters. Over-long input is refused before hashing.

## Known gaps and follow-ups

- **Old accounts can't log in.** They have no password. Their plans stay in the database under those accounts.
- **No password reset or change, and no limit on login attempts.**
- **This isn't HIPAA compliance.** Hashed passwords and per-account access are the basics. HIPAA would also need things like a signed agreement with the database host, audit logging and encryption policies.
